# 编写功能工作流程文档

本 skill 用于在 `doc/` 目录下创建与维护**系统/功能工作流程文档**，记录某个子系统（如渲染、实体、蓝图编辑、属性修改）从输入到输出的完整链路。所有产出**必须与 `doc/engine/`、`doc/editor/` 现有文档保持同一套结构与语气**，使整个文档体系连贯可索引。

> ⚠️ 本 skill **只写"系统/功能工作流"类文档**（什么是、怎么运转、有哪些类/接口、谁依赖谁、何时谁触发谁）。**不写**下列内容——它们应由对应专项 skill 承担：
> - 业务资产创建（场景/蓝图/配置/UI widget）→ 用 `create-*-asset` 系列 skill
> - 操作手册 / Quick Start（"怎么新建项目"）——不属于系统设计

## 1. 何时使用

- 用户要求新建/重写某个子系统的设计文档（"写一下 XX 系统的文档"、"整理 YY 的工作流"）
- 给一个已有但没文档的功能补文档（"XX 这块没有文档，写一份"）
- 某子系统发生重大重构后更新对应文档（描述/接口/流程变了）

如果用户给的描述只覆盖"做一个具体的东西"（例：写一个鱼、写一张配置表），**不要**用本 skill——那是资产创建任务，应转去对应的 `create-*-asset` skill。

## 2. 建立文档前的强制步骤

1. **先读 `doc/README.md`**：确认这是引擎系统还是编辑器系统，决定文件落在 `doc/engine/` 还是 `doc/editor/`，避免放错目录导致索引表错位。
2. **复用现有文档风格**：打开同目录下任意一份现有文档（如 `doc/engine/entity_system.md`、`doc/editor/blueprint/blueprint_edit_system.md`）作模板，照抄章节标题顺序与语气。**不要自创章节顺序**。
3. **用代码事实校验**：通过 `read_file` / `grep_search` 读真实源码确认每个接口签名、类名、字段、调用关系。**禁止凭印象或常识描述 API**—— DemoStudio 的命名/层级经常反直觉（例如"顶层 transform 已废弃，必须写进组件"这类约定只能从代码里读出来）。文档里每一处类名/方法名/字段名都必须能在源码里 `grep_search` 到。
4. **不要重复造轮子**：先用 `grep_search` 查 `doc/` 下是否已有重叠文档；若某部分已被其他文档覆盖，用相对链接引用，不要复制内容。

## 3. 文档统一结构（必须照此顺序）

文档围绕**三个核心部分**展开：**使用方法**（怎么调）、**工作流程**（内部怎么运转）、**边界条件**（什么情况下不能用/会失败）。章节顺序固定如下：

```
# <功能中文名>（<English Name>）

> 一句话定位 + 代码位置（src/... 的具体目录/文件）+ 相关文档链接（相对路径）
> 相关文档链接至少放一条指向 system_overview.md 或同子域的姊妹文档

## 1. 概述
3~6 段，说清楚：
- 这个功能解决什么问题、在引擎/编辑器中处于什么位置
- 关键角色（谁产生数据、谁消费、谁协调）
- 一开始就给一张责任表把"谁干什么"列清楚（模仿 entity_system.md §1 的四级表 / property_edit §1 的双通道表）
- 与相邻功能的边界（功能 A 归本文档，功能 B 归 X 文档）

## 2. 核心类 / 模块
（引擎系统用"核心类"；编辑器系统用"核心模块"）
| 类 / 模块 | 说明 |
表格化，一行一个，说明列写职责不要罗列 API。

## 3. 使用方法
面向"想调用这个功能的人"，回答"怎么用"：
- 入口 API：对外暴露的函数/接口/命令/事件，用 ```ts 代码块给签名，注释/简表写明参数含义与返回值
- 调用示例：```ts 最小可用示例（谁调、传什么、得到什么）
- 触发时机：什么时候被调用（用户操作？AI 指令？游戏 tick？事件回调？）
- 使用前提：调用前必须先做什么（初始化/注册/切换场景/组件挂载）

## 4. 工作流程
面向"想理解内部机制的人"，回答"怎么运转"。必须分小节：
- 4.1 主流程：用 ```mermaid flowchart 把从触发到落盘/生效的完整链路画出来
- 4.2 分阶段说明：主流程每个阶段的职责与关键函数（可表格：阶段 | 触发点 | 关键调用 | 产物）
- 4.3 设计要点：每条要点单独小标题，讲清"为什么这么设计"
  - 数据流向：上游→本系统→下游
  - 双通道/多通道逻辑（如有，参照 property_edit 双通道表）
  - 关键约束/约定（违反会出 bug 的硬规则，参照 scene asset 的"组件优先约定"）
- 流程图节点文字要具体，写真实的方法/状态名（"dispatch(op)"、"op 合法?"），不要写"处理一下"、"判断逻辑"

## 5. 边界条件
面向"想安全使用的人"，回答"什么情况下不能用/会出问题"。用表格逐条列：
| 条件 | 行为/后果 | 处理方式 |
至少覆盖：
- 输入边界：参数范围/必填项/非法值的行为（报错？静默忽略？截断？）
- 失败场景：什么情况会失败、失败后行为（抛异常？返回错误？回滚？进撤销栈？）
- 状态约束：哪些时机/状态下不允许调用（未初始化、场景未加载、组件未挂载、编辑器模式限制）
- 数量/性能边界：上限、递归深度、O(n) 代价、高频调用注意点
- 已知限制：当前实现明确不支持/未实现的场景

## 6. 依赖关系 / 注册机制
（二选一或都写，看功能是否有明显依赖/注册）
- 依赖关系用 ``` 代码块画 ASCII 箭头链
- 注册机制引用相邻文档（如 Actor/Component 的注册指向 asset_tools_system.md）

## 7. （可选）踩坑记录 / 历史决策
仅当用户提到了"以前踩过的坑"或文档已有这一节时才加。写真实发生过的事：现象/原因/约束。不要编造。
```

### 关键规则总结

- **章节顺序与编号不可变**（1 概述 → 2 核心类/模块 → 3 使用方法 → 4 工作流程 → 5 边界条件 → 6 依赖/注册 → 7 踩坑（可选））；其中 **§3 使用方法、§4 工作流程、§5 边界条件是必写核心**，缺一不可
- **小标题数字编号**（`### 3.1`、`### 4.2`），数据用表格、链路用 mermaid、接口用 ts 代码块
- **代码位置必须写**（文档头部 `>` 和 §2 表都写明 `src/...`）
- **跨文档一律相对路径链接**（`../system_overview.md`、`./entity_system.md`）
- **不出现"可能"、"大概"、"应该"**——所有断言要么有源码支撑，要么标注为未确认并查证
- **§3 使用方法的示例代码必须能直接跑通**（从源码入口处抄真实调用写法，不要发明 API）

## 4. 收集信息的标准动作（避免漏事实）

按以下顺序排查源码，缺一项就回头补：

1. **入口/调度入口**：`grep_search` 系统名 / 核心类名，找出"谁第一个调用它"（Editor 初始化？GameInstance tick？事件回调？）
2. **数据结构**：读类型定义文件（`*.ts` 里的 interface/class），把字段、类型、默认值、注释完整记下
3. **主链路**：从入口顺着 `read_file` 跟到落盘/生效点，标出每一步调的函数名
4. **失败/撤销/重试分支**：找 `catch` / `rollback` / undo，文档里单独成节
5. **注册机制**：grep 系统中类的注册语句（`XXXRegistry.register` / `import.meta.glob`）
6. **相邻系统边界**：看 import 谁的、被谁 import，避免越界写别人子系统的细节

> 写完每一节前问自己：**这节里出现的每个类名/方法名，我能在源码里 grep 到吗？** 不能就不要写出来。

## 5. 建立新文档后的强制动作

**写完文档后必须更新 `doc/README.md`**：

- 在对应分类表格（"引擎系统" / "编辑器系统" / "专题文档"）下一行追加
- 格式严格照搬现有行：`| [\`engine/xxx_system.md\`](./engine/xxx_system.md) | <一句话说明括号补定位> |`
- 一句话说明**不要超过表里现有行的详细程度**（控制在 20~30 字以内，写清"是什么 + 何时查它"）

**可选**：如果改动涉及顶层架构统计，查看 `doc/system_overview.md` 是否有该子系统的统计条目需要同步——大多数新增文档**不需要动**它，只有当 `system_overview.md` 明确列出过该类型时才同步。

## 6. 重写/更新已有文档的差异

当任务是"更新现有文档"而不是"新建"时：

1. 先 `read_file` 原文全量，列出哪些章节与代码现状不符
2. **保留原有章节编号与小标题**，只替换过时内容
3. 如果代码新增了子能力（比如组件多了字段、流程多了分支），在对应章节里**追加小节**而不是重写大节
4. 如果原文缺少三大核心部分中的某一节（如没有"边界条件"），**补齐该节**再更新，不要只补在尾部堆叠
5. 不要删除原"踩坑记录/历史决策"——那是历史信息不是冗余

## 7. 完成检查清单（产出前自查）

- [ ] 文件落在了 `doc/engine/` 或 `doc/editor/`（由 README.md 分类决定）
- [ ] 头部 `>` 块含：一句话定位 + `代码位置：src/...` + 至少 1 条相关文档相对链接
- [ ] 章节顺序为：概述 → 核心类/模块 → 使用方法 → 工作流程 → 边界条件 → 依赖/注册
- [ ] **§3 使用方法**：有入口 API 签名 + 可跑通的调用示例 + 触发时机/使用前提
- [ ] **§4 工作流程**：有 mermaid 主流程图 + 分阶段说明（+ 设计要点小节）
- [ ] **§5 边界条件**：有表格逐条列出输入边界/失败行为/状态约束/数量性能限制/已知限制
- [ ] §1 有责任划分表
- [ ] 所有类名/方法名/字段名在源码里 grep 得到
- [ ] 跨文档链接用相对路径
- [ ] `doc/README.md` 的对应表格已追加本文件条目
- [ ] 没有"可能/大概/应该"，所有断言有源码依据

新文档请对照这两份范本的章节与笔触：
- 引擎系统范本：`doc/engine/entity_system.md`（四级对象层级 + 组件 + 依赖 + 注册）
- 编辑器系统范本：`doc/editor/blueprint/blueprint_edit_system.md`（含 mermaid 流程图 + 三层校验表）与 `doc/editor/core/property_edit_system.md`（含双通道表 + 四步添加属性小节）
