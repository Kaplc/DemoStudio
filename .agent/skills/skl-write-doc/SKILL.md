# 编写功能工作流程文档

本 skill 用于在 `doc/` 目录下创建与维护**系统/功能工作流程文档**，记录某个子系统（如渲染、实体、蓝图编辑、属性修改）从输入到输出的完整链路。所有产出**必须与 `doc/engine/`、`doc/editor/` 现有文档保持同一套结构与语气**，使整个文档体系连贯可索引。

> ⚠️ 本 skill **只写"系统/功能工作流"类文档**（什么是、怎么运转、有哪些类/接口、谁依赖谁、何时谁触发谁）。**不写**下列内容——它们应由对应专项 skill 承担：
> - 业务资产创建（场景/蓝图/配置/UI widget）→ 用 `create-*-asset` 系列 skill
> - 操作手册 / Quick Start（"怎么新建项目"）——不属于系统设计

## 1. 何时使用

- 用户要求新建/重写某个子系统的设计文档（"写一下 XX 系统的文档"、"整理 YY 的工作流"）
- 给一个已有但没文档的功能补文档（"XX 这块没有文档，写一份"）
- 某子系统发生重大重构后更新对应文档（描述/接口/流程变了）

如果用户给的描述只覆盖"做一个具体的东西"（例：写一个鱼、写一张配置表），**不要**用本 skill——那是资产创建任务，应转去对应的 `create-*-asset` skill。

## 2. 建立文档前的强制步骤

1. **先读 `doc/README.md`**：确认这是引擎系统还是编辑器系统，决定文件落在 `doc/engine/` 还是 `doc/editor/`（编辑器文档再按主题落二级子目录 `core/`、`blueprint/`、`asset/`、`ui/`、`integration/`，见 README.md §3），避免放错目录导致索引表错位。
2. **复用现有文档风格**：打开同目录下任意一份现有文档（如 `doc/engine/entity_system.md`、`doc/editor/blueprint/blueprint_edit_system.md`）作模板，照抄章节标题顺序与语气。**不要自创章节顺序**。
3. **用代码事实校验**：通过 `read_file` / `grep_search` 读真实源码确认每个接口签名、类名、字段、调用关系。**禁止凭印象或常识描述 API**—— DemoStudio 的命名/层级经常反直觉（例如"顶层 transform 已废弃，必须写进组件"这类约定只能从代码里读出来）。文档里每一处类名/方法名/字段名都必须能在源码里 `grep_search` 到。
4. **不要重复造轮子**：先用 `grep_search` 查 `doc/` 下是否已有重叠文档；若某部分已被其他文档覆盖，用相对链接引用，不要复制内容。

## 3. 文档结构（必须照此顺序）→ 见 §3.1 新范式

### 3.1 写作第一原则：写给「十分钟要上手的新人」

**旧范式（禁止再写）**：概述 → 核心类表格 → 使用方法 → 工作流程 → 边界条件 → 依赖 → 踩坑。这种结构看起来完整，但新人读完只会得到一堆 API 名字，不知道代码从哪进、从哪出。

**新范式（照此写）**：

1. **开篇三问**（头部 `>` 块内，用加粗标签）：一句话定位 / 什么时候会用到你 / 代码位置
2. **先记住这几个文件**：新人只需要先认 2~4 个文件，配「你要改它的场景」列，其余遇到再看
3. **流程讲解 = 真实代码 + 逐段白话**：贴**源码原文**（从 `read_file` 真实抄来，可裁剪注释和无关分支但不得改写逻辑），每段代码下面紧跟一段讲解，说明「这步干了什么、为什么这么写、不这么写会怎样」
4. **关键方法速查表**：`方法 | 位置（文件:行号）| 干什么 | 注意`
5. **流程影响 = 上游/下游表 + 相关文档链接列**（不再写"越界与冲突"这种抽象段落）
6. **踩坑清单**：编号条目，每条「现象 → 原因 → 规则」，只写真踩过的
7. **边界条件**：表格，收尾

### 3.2 章节骨架

```
# <功能中文名>（<English Name>）

> **一句话定位**：...
> **什么时候会用到你**：...（列举具体场景：新增 XX 时、排查 XX 时）
> 代码位置：`src/...`

## 1. 先记住这几个文件
| 文件 | 一句话职责 | 你要改它的场景 |

（可选：给一段「关键心智模型」——这个功能最容易误解的一点）

## 2. <主流程名>：从 <起点> 到 <终点>
### 2.1 谁调用了它      —— 贴真实调用代码
### 2.2 <流程名> 内部做的 N 件事   —— mermaid 流程图
      逐段讲代码 —— 贴源码 + 讲解，编号 ①②③
### 2.3 <收尾/异常分支>  —— 贴代码 + 讲解

## 3. <第二条主链路/交互路径>是怎么流进来的   —— mermaid + 表格 + 代码片段

## 4. 关键方法速查
| 方法 | 位置 | 干什么 | 注意 |

## 5. 流程影响：牵动哪些功能
### 上游：谁驱动它        | 上游 | 怎么驱动 | 相关文档 |
### 下游：它波及谁        | 下游功能 | 波及点 | 相关文档 |

## 6. 踩坑清单（都是真踩过的）
**N. <现象>** —— 原因 + 规则（可贴代码）

## 7. 边界条件
| 条件 | 行为 | 怎么应对 |
```

### 3.3 硬性要求

- **代码必须真实**：每一段代码都从 `read_file` / `grep_search` 的真实结果里抄，禁止凭印象写 API。可以删注释、删无关分支，但**不得改写逻辑或发明方法名**
- **代码要配讲解**：贴完代码必须紧跟讲解，说明这步的作用与设计动机（尤其是反直觉的写法：为什么 `void` 不 await、为什么要等 600ms、为什么要清 undefined）
- **方法位置写行号**：`Editor.ts:38` 这种形式，让新人能直接跳过去
- **流程影响必须带文档链接**：表格最后一列是「相关文档」，相对路径链接到对应功能点文档
- **不写无信息量的内容**：纯 API 罗列表、能一眼看出的废话、「本模块负责协调各模块」这类空话一律删掉
- **mermaid 节点写真实方法名**：`dispatch(op)`、`op 合法?`，不要写「处理一下」
- **章节编号可灵活**：新范式不强制八章编号，按内容需要增删，但**顺序不能乱**
```

### 关键规则总结（新范式版）

- **章节顺序按 §3.2 骨架**，其中**开篇三问、先记住这几个文件、关键方法速查、流程影响、踩坑清单、边界条件是必写核心**，缺一不可
- **小标题数字编号**（`## 2.`、`### 2.1`），数据用表格、链路用 mermaid、接口用 ts 代码块
- **代码位置必须写**（文档头部 `>` 块内标注 `src/...`）
- **跨文档一律相对路径链接**（`../system_overview.md`、`./core_system.md`）
- **跨文件链接指向源码**（`[Editor.ts](../../../src/editor/Editor.ts)`），让新人能一键跳到真实代码
- **不出现"可能"、"大概"、"应该"**——所有断言要么有源码支撑，要么标注为未确认并查证
- **示例代码必须能直接跑通**（从源码入口处抄真实调用写法，不要发明 API）

## 4. 收集信息的标准动作（避免漏事实）

按以下顺序排查源码，缺一项就回头补：

1. **入口/调度入口**：`grep_search` 系统名 / 核心类名，找出"谁第一个调用它"（Editor 初始化？GameInstance tick？事件回调？）
2. **读源码全文**：核心文件用 `read_file` **整篇读进来**——新范式要求贴真实代码逐段讲解，只读片段会导致讲解与代码对不上
3. **定位关键方法行号**：用 `grep_search` 找方法定义所在行，方法速查表要写 `文件:行号`
4. **主链路**：从入口顺着 `read_file` 跟到落盘/生效点，标出每一步调的函数名
5. **失败/撤销/重试分支**：找 `catch` / `rollback` / undo，作为独立小节
6. **反直觉写法**：重点找「为什么这么写」的证据——`void` 不 await、`setTimeout` 等待、清理 undefined、可选链、幂等标记、HMR 守卫。这些是踩坑清单的素材
7. **注册机制**：grep 系统中类的注册语句（`XXXRegistry.register` / `import.meta.glob`）
8. **相邻系统边界**：看 import 谁的、被谁 import，确定流程影响表该链接哪些文档

> 写完每一节前问自己：**这节里出现的每个类名/方法名，我能在源码里 grep 到吗？贴的这段代码是我从源码里抄来的吗？** 不能就不要写出来。

## 5. 建立新文档后的强制动作

**写完文档后必须更新 `doc/README.md`**：

- 在对应分类表格（"引擎系统" / "编辑器系统" / "专题文档"）下一行追加
- 编辑器系统文档落到 `doc/editor/<子目录>`（core/blueprint/asset/ui/integration），在 README.md §3 对应二级小节的表格里追加
- 格式严格照搬现有行：`| [\`engine/xxx_system.md\`](./engine/xxx_system.md) | <一句话说明括号补定位> |`
- 一句话说明**不要超过表里现有行的详细程度**（控制在 20~30 字以内，写清"是什么 + 何时查它"）

**可选**：如果改动涉及顶层架构统计，查看 `doc/system_overview.md` 是否有该子系统的统计条目需要同步——大多数新增文档**不需要动**它，只有当 `system_overview.md` 明确列出过该类型时才同步。

## 6. 重写/更新已有文档的差异

当任务是"更新现有文档"而不是"新建"时：

1. 先 `read_file` 原文全量，列出哪些章节与代码现状不符
2. **范式升级**：若目标文档仍是旧范式（概述 → 核心类表格 → 使用方法 → …），按 §3.1 新范式整体重写，不要只补章节
3. **重写前必须重读源码**：新范式要求贴真实代码，靠旧文档的内容推不出代码细节
4. 如果代码新增了子能力（比如组件多了字段、流程多了分支），在对应章节里**追加小节**而不是重写大节
5. 不要删除原"踩坑记录/历史决策"——把真实踩过的坑迁移到新的「踩坑清单」章节，那是最有价值的部分
